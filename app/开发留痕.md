## 三、ArkTS 的坑（第 ② 步）

### 坑 1：禁止匿名对象字面量

```typescript
// ❌ 编译失败
out.push({ type: 'function', function: { name: def.name } } as Object);
```

```
arkts-no-untyped-obj-literals
Object literal must correspond to some explicitly declared class or interface
```

**为什么 ArkTS 这样设计**：它要编译成字节码，**必须在编译期确定每个对象的结构**。
匿名字面量无法确定类型，所以禁止。

**修法**：为每个结构声明显式接口。`Agent.ets` 里因此定义了 **13 个接口**：

```typescript
interface PropSchema { type: string; description: string; }
interface ParamSchema  { type: string; properties: Record<string, PropSchema>; required: string[]; }
interface FunctionSchema { name: string; description: string; parameters: ParamSchema; }
interface ToolSchema { type: string; function: FunctionSchema; }
```

**连带约束**：`Map` 不能直接进对象字面量，`properties` 必须用 `Record`：

```typescript
// ❌
const props = new Map<string, Object>();
props.set(p.name, {...});
// ✅
const props: Record<string, PropSchema> = {};
props[p.name] = { type: p.type, description: p.description };
```

### 坑 2：`@ts-ignore` 被禁止

```typescript
// @ts-ignore     → ✗ arkts-strict-typing-required
import speechRecognizer from '@hms.ai.speechRecognizer';
```

**ArkTS 不允许关掉类型检查。** 这条很关键——它堵死了「遇到类型问题就压制」这条路。

### 坑 3：命名空间不能当对象

```typescript
const kit = await import('@kit.CoreSpeechKit');
const sr = kit.speechRecognizer;    // ✗ arkts-no-ns-as-obj
```

### 坑 4：不支持结构化类型

```typescript
// ✗ arkts-no-structural-typing
const engine: TtsEngine = officialEngine;   // 即使字段对得上也不行
```

**这四条合起来说明一件事**：ArkTS 的类型系统是**名义的、严格的**，
不能靠「长得像」来兼容。这是和 TypeScript 最大的区别。

## 四、ArkTS 报错的解读方法（最实用的技能）

**ArkTS 的错误码本身很有信息量**，学会看码比搜索快：

| 错误码前缀 | 含义 | 例子 |
|---|---|---|
| `arkts-no-untyped-obj-literals` | 匿名对象字面量 | 要声明接口 |
| `arkts-no-ns-as-obj` | 命名空间当对象 | 换 import 方式 |
| `arkts-strict-typing-required` | 关了类型检查 | 不能 @ts-ignore |
| `arkts-no-structural-typing` | 结构化类型 | 必须同名类型 |
| `arkts-no-ambient-decls` | 环境声明 | 不能 declare module |
| **`11706007`** | **跨平台不支持** | **平台特有 API 进了共享代码** |

**`11706007` 这条要特别记住**——它说的是「这个 API 不能用在 ArkUI-X 跨平台工程里」，
不是语法错、不是用法错，**是设计边界**。

## 五、四个真实 bug 是怎么定位的

### bug ①：多轮对话 400 错误（最典型）

**现象**：第一轮正常，第二轮报错

```
Messages with role 'tool' must be a response to a preceding message with 'tool_calls'
```

**定位过程**：

1. 先看错误本身——它说得很清楚：`tool` 消息必须**跟在带 `tool_calls` 的 assistant 消息后面**
2. 检查我的代码，发现 `callModel()` 里重建历史时**把 `tool_calls` 丢了**：

```typescript
// ❌ 有 bug 的写法
} else if (m.role === 'assistant') {
  wire.push({ role: 'assistant', content: m.content });   // tool_calls 没了！
}
```

3. 想清楚**为什么第一轮不报错** —— 第一轮消息是当轮新建的、结构完整；
   **第二轮带上历史时**，`tool` 结果还在但 `assistant.tool_calls` 没了 → 孤儿消息

**修法**：历史直接以 wire 格式保存，保留成对结构
（`assistant(tool_calls)` ↔ `tool(tool_call_id)`）。

**能学到什么**：
> **「只在第二轮才出现」的 bug，往往和历史状态有关。**
> 测试时一定要跑多轮，不能只测第一轮。

### bug ②：工具超时（静默失败最坑）

**现象**：Agent 说「查不到」，但网络是通的

**定位过程**：

1. 先确认网络（模拟器 `ping codeforces.com` → 通）
2. 看代码，发现 `ensureLoaded()` **每次都拉全量题库表**（约 2 MB / 5000+ 题）
3. 更关键的是发现**异常被吞掉了**：

```typescript
// ❌ 有 bug 的写法
try {
  this.info = await this.client.userInfo();
} catch (e) {
  this.info = null;      // 异常消失，后面就显示「还没记录」
}
```

**结果**：真实的故障（超时）完全看不到，**排查时被引向错误方向**。

**修法**：
- 题库表改为后台懒加载（不 `await`）
- **失败原因记住并抛出**，让模型看到真实错误

**能学到什么**：
> **吞异常是最坏的错误处理。** 至少要把原因带出去。
> 一个 `catch (e) { }` 能让排查多花几小时。

### bug ③：语音「松手没反应」（竞态）

**现象**：按「说」按钮没反应

**定位过程**：

1. 先看日志——发现**引擎其实启动成功了**：
   ```
   HiAI_ASR_AsrEntryManager: calling startListening
   ReportCoreManager: result_code: "0", message: "success"
   ```
2. 说明业务逻辑开始执行了，问题在**更早的地方**
3. 检查代码发现竞态：

```typescript
private async startVoice() {
  const granted = await this.requestMic();   // ← 异步，首次要等权限弹窗
  this.listening = true;                     // ← 这里才置位
}
private stopVoice() {
  if (!this.listening) return;               // ← 松手时还没置位 → 直接返回
}
```

**修法**：加 `released` 标记记住「用户已松手」，启动完成后自己收尾。

**能学到什么**：
> **异步操作期间的用户操作必须用「意图标记」记下来**，
> 不能靠状态变量判断——因为状态还没更新。

### bug ④：热词导致引擎创建失败（错误码救命）

**现象**：`createEngine` 失败，错误信息是空的 `msg`

**定位过程**：

1. 先改代码**把 `code` 也带出来**（因为只有 message 时经常是空串）：
   ```typescript
   const code = err.code ?? -1;
   cb.onError(`启动识别失败（code=${code}）`);
   ```
2. 从日志拿到关键两行：
   ```
   E AI_TEXT: [CheckLexicons] lexicons length exceeds limit, length: 21
   W AI_TEXT: [ParseAsrEngineOptions] not system app! reset config to default
   ```
3. **查证发现矛盾**：文档说「最多 200 个热词、每个 2–20 字」，
   而我的表是 79 个词、每个 2–7 字，**完全合规**
4. 所以问题不在热词表本身，而在 `not system app` 那条 ——
   **非系统应用不允许配热词**

**修法**：去掉热词（它只是识别率优化项，非必需）。

**能学到什么**：
> **错误信息不完整时，先补全诊断信息再排查。**
> 如果我只打印 `err.message`（空串），这个 bug 会卡很久。

## 六、三个架构决策

### 决策 1：为什么知识检索用关键词而不是向量

| 方案 | 体积 | 精度 |
|---|---|---|
| 语义索引（bge-small + reranker） | **42 MB** | 高 |
| 关键词索引 | **145 KB** | 够用 |

**为什么够用**：检索目标是「把用户说的词映射到一个词条」，
不是问答理解。用户问的是确定的算法名（「线段树」「KMP」），不需要语义泛化。

**实测**：25 个常见查询，**25/25 命中**（但要承认这是我自己挑的用例）。

### 决策 2：为什么语音要开两个工程

**这是本项目最有技术含量的一处判断。**

课程两条要求**直接冲突**：

| 要求 | 冲突 |
|---|---|
| 一套代码 → 鸿蒙 + Android | ArkUI-X 要求代码跨平台兼容 |
| 鸿蒙端必须打通语音 | 语音 API **不是**跨平台 API |

**验证过程（9 种写法全部实测失败）**：

| # | 尝试 | 失败原因 |
|---|---|---|
| 1 | 静态 `import` | `11706007 can't support crossplatform` |
| 2 | 接口 + 空实现 | 编译过，但鸿蒙端也没语音了 |
| 3 | 动态 `import()` | 拿不到模块 |
| 4 | `const m = kit.speechRecognizer` | `arkts-no-ns-as-obj` |
| 5 | `import('@hms.ai.xxx')` | 同上 |
| 6 | `@ts-ignore` | `arkts-strict-typing-required` |
| 7 | `declare module` | `arkts-no-ambient-decls` |
| 8 | 动态 import + 链式调用 | `11706007` 又出现 |
| 9 | 自定义 interface 适配 | `arkts-no-structural-typing` |

**结论**：框架层面无法共存 → **方案 C：双工程 + 共享业务代码**

```
greedy-app      跨端工程（满足要求 1）  —— 语音降级
greedy-harmony  单端工程（满足要求 2）  —— 语音真实现
```

**共享边界靠 `sync_shared.py` 保证**：共享 12 个文件，平台特有 1 个。

### 决策 3：会话持久化只存问答，不存工具中间消息

**为什么不存**：
- 体积大（一次工具结果可能几千字符）
- **结构脆弱**：`assistant(tool_calls)` 与 `tool(tool_call_id)` 必须成对，
  跨会话恢复时一旦对不上，接口直接 400（就是 bug ① 的同一个坑）

**重放时**只需要让模型知道「之前聊过什么」，**不需要原样的工具轨迹**。
